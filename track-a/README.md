# Track A: Ingest

Reads 3,100,000 HTTP request log lines and, for every hour and endpoint that saw traffic, writes the request count, the nearest-rank p50, p95 and p99 latency, and the number and rate of 5xx responses.

Rust, standard library only. a-66 on the box (12 workers, fresh tmpfs /out per run, 15 interleaved rounds): T median 15.29 ms, level with a-65, memory peak 16.4-17.2 MB, S 394 against a-65's 430 (393, plus one check on the input mapping): expected K +1.4 %. Board: a-66's first run, run-0814c130face, read T 18.80 ms, K 50.70; one board run of unchanged code varies that much (a-65's code ran 15.61, 16.56 and 18.88 ms). a-65's best, run-ffd993386390: K 55.90 (T 15.61 ms, M 16.5 MB, S 430, A rank 5); a-64 K 55.02 (T 16.06 ms, M 17.4 MB, S 430).

Reproduce with seed 1's full data in `<data>`, then compare the hash with the full seed-1 output hash in the [spec](https://github.com/hackathon-raptors/speed-demon-2026/blob/main/specs/a-ingest.md):
`docker build -t a track-a && docker run --rm --network=none -v <data>:/data:ro -v <out>:/out a && sha256sum <out>/summary.txt`

Moving the mapping's release (a-57 LOST list) does not help: the unmap costs ~2 ms wherever it lands.

## Approach

Rust, standard library only. The binary links the C runtime statically (probe a-26), so no dynamic loader runs before main. The program maps `/data/requests.log` read-only (`src/main.rs` `main`) and claims it in 1 MiB blocks in file order (`Job::align`, `Job::work`). Each thread walks its claimed blocks (`Job::parse`), looking each endpoint up in one shared table (`Job::id`) and writing each line as a 32-bit row, (global endpoint id + 1) << 21 | 5xx << 20 | latency, into its hour's region (`Job`, a-59): a thread claims 256 rows of an hour at a time, so a row needs no atomic. A latency of 2^20 - 1 or more (0.24 % on seed 1) goes to the hour's long list instead (a Vec under a lock), as latency << 32 | the row without it.

The pipeline finishes hours as soon as the registered prefix of the file holds a line two hours later (LAG 2), so threads do not wait for the whole scan to complete (`Job::work`). If a line arrives for an hour that was already claimed for finishing, the run is marked late, and `main` repeats the entire run with no early finishing (LAG = HOURS), ensuring the output is exact for any line order (`run`, `main`).

Each line is read forward from its start, and the next line starts where its latency's digits end, so no LF is searched for first (`Job::parse`, a-62). The timestamp is always 27 bytes, so one 64-byte space mask from byte 28 ends the method and, unless the endpoint is long, the endpoint; the 3-digit status follows, and one 8-byte load finds the latency's digits up to the LF (`line`, a-62), converted with two multiply-adds (`digits8`, a-56). Two prefetches ask for the bytes 1.3 KB ahead on every line, since the hardware prefetcher stops at each 4 KiB page. The hour is checked with one u64 load of "MM-DDTHH" against the previous line's.

Endpoints are looked up in one table shared by all threads (`Job::id`, a-63; the shape is AVENGERS' public track A): open addressing over 8,192 slots, under a quarter full. The hash covers the whole name without a loop: the first and last 32 bytes, each cut to the name with a compare against the lane numbers, and from 65 bytes on the two loads over its middle (spec 2: at most 125 bytes), mixed by AES rounds that work on both 16-byte halves at once, the length a round key (`ep_hash`). 53 bits of the hash are the endpoint's identity and the slot's low 11 bits hold its id, so a lookup is one load and one compare, with no byte compare: for 1,842 endpoints the chance that two share those 53 bits is about 2e-10. New names are pushed under a lock, which a thread takes only when it finds an empty slot; the table fills in the first moments and is then only read, one copy in every core's cache. Finishing threads sort new ids in byte order (`Job::order`). Against a-62's private tables with a masked byte compare: user instructions 579 -> 520 M, L1 misses 4.3 -> 2.5 M, 71 fewer lines.

Memory is kept small (a-59, a-60): the hours' regions sit in one anonymous MAP_NORESERVE reservation, so only the pages rows touch cost anything; an hour's text is written over its rows, and once it is written the region goes to a pool of one (`Job::region`), from which the next hour takes it with its pages already faulted in; when the pool is full a region is given back (MADV_DONTNEED). A fresh region per hour (a-59) cost ~7,000 page faults a run; an unbounded pool grew to 11 regions and +3.8 MB of peak, one costs ~+0.6 MB. A pooled region holds an older hour's bytes, so each claimed chunk of 256 rows is zeroed first (a row no line takes must read 0). Transparent huge pages are turned off (PR_SET_THP_DISABLE): with THP on (the box's setting), an hour's first row charged a 2 MiB page and the peak doubled. Nothing large is allocated by malloc. Once all hours are claimed, threads release the input mapping's page-table entries in shared 4 MiB steps (in `Job::work`, a-12, a-55) so process exit has fewer to tear down.

The tail runs in parallel as hours become ready (`Job::finish`, a-58, a-61): one pass counts each hour's rows per endpoint and 5xx flag and builds two histograms of the latency, its low 9 bits (512 entries) and its high 11 (2,048); two stable counting passes (`deal`) then sort the rows by latency, using the region past the rows as the other buffer, and a last pass deals them to each endpoint's span in byte order (free slots go to one trash slot, so the pass has no branch). A stable deal keeps each span sorted, so p50, p95 and p99 are read off by rank. The few latencies of 2^20 - 1 or more sit in the hour's long list as latency << 32 | row, which order by latency: one sort, then they are appended to their spans. Until a-60 a quickselect per span (AVX2 partition, bitonic base case) did the ranks: as fast in instructions (671 M against 676 M a run) and 0.9 ms faster, but 132 more lines and a scratch buffer per thread (+0.9 MB of peak). The text goes over the rows; hours are placed in hour order and each is written at its offset with `pwrite`, so finishing threads write at once (in `Job::work`).

The worker count is `available_parallelism`; `SD_WORKERS` overrides it for the hash tests only. Each output number below 10^8 is made at once in one u64, the leading zeros shifted out, and one 8-byte store writes it; larger ones take two u64s and a 16-byte store (`put`, `decimal8`).
